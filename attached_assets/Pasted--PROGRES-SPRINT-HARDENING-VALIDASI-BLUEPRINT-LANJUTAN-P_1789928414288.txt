### ✅ Task #18: Resilience Ekstraksi Dokumen Setelah Server Restart

**Mengapa ini kritis di KontrakGuard:**
Dalam konteks konstruksi, dokumen yang gagal diekstrak = klausul kontrak yang tidak teranalisis = deadline yang tidak terdeteksi = hak klaim yang hangus. Ini bukan masalah teknis biasa, ini masalah **liabilitas hukum**.

**Pattern yang harus divalidasi:**

```python
# tests/document_extraction/test_resilience.py

class TestExtractionResilience:
    
    async def test_extraction_resumes_after_crash(self):
        """Job ekstraksi harus lanjut dari checkpoint, bukan ulang dari awal"""
        doc = await upload_large_contract(pages=500)
        job_id = await start_extraction(doc.id)
        
        # Simulasi crash di halaman 250
        await simulate_crash_at_page(job_id, page=250)
        await restart_server()
        
        # Job harus auto-resume
        await wait_for_completion(job_id, timeout=300)
        
        result = await get_extraction_result(doc.id)
        assert result.status == "COMPLETED"
        assert result.pages_processed == 500
        assert result.checkpoint_resume_at == 250  # Tidak ulang dari 0
    
    async def test_idempotent_extraction(self):
        """Retry 3x harus hasilkan output identik"""
        doc = await upload_contract("sample.pdf")
        
        results = []
        for _ in range(3):
            await reset_extraction(doc.id)
            result = await run_extraction(doc.id)
            results.append(result.checksum)
        
        assert len(set(results)) == 1, "Ekstraksi tidak deterministik"
    
    async def test_dead_letter_queue_for_permanent_failures(self):
        """Dokumen korup tidak boleh block queue selamanya"""
        corrupt_doc = await upload_corrupt_pdf()
        await start_extraction(corrupt_doc.id)
        
        # Setelah 3x retry, masuk dead letter queue

        dlq_item = await get_dead_letter_item(corrupt_doc.id)
        assert dlq_item is not None
```

### ✅ Task #19: Skema Database Selalu Sinkron di CI

**Mengapa ini kritis:**
Bug "kolom tidak ada" yang lolos ke production bisa menyebabkan downtime saat migration berjalan. Di KontrakGuard yang menangani dokumen hukum, downtime = potensi kehilangan hak klaim.

**Strategi yang harus diimplementasi:**

```yaml
# .github/workflows/ci.yml (atau GitLab CI equivalent)
name: Integration Tests
on: [push, pull_request]

jobs:
  integration-tests:
    steps:
      - name: Start PostgreSQL
        run: docker-compose up -d postgres
        
      - name: Wait for DB
        run: pg_isready -h localhost -U postgres
        
      - name: Run ALL migrations from scratch
        # Ini kunci: mulai dari database kosong, bukan dari state sebelumnya
        run: |
          psql -h localhost -U postgres -c "DROP DATABASE IF EXISTS kontrakguard_test;"
          psql -h localhost -U postgres -c "CREATE DATABASE kontrakguard_test;"
          npm run migrate:up -- --database kontrakguard_test
          
      - name: Verify schema matches expected
        # Deteksi schema drift antara code dan database
        run: npm run schema:verify
        
      - name: Run integration tests
        run: npm run test:integration
        
      - name: Verify migrations are reversible
        # Pastikan rollback bisa dijalankan
        run: |
          npm run migrate:down -- --database kontrakguard_test
          npm run migrate:up -- --database kontrakguard_test
```

**Schema drift detector:**

```python
# scripts/verify_schema.py

def verify_schema():
    """
    Deteksi jika ada kolom/tabel di code yang tidak ada di DB,
    atau sebaliknya (indikasi migration lupa dibuat).
    """
    expected = load_schema_from_code()  # dari SQLAlchemy/Prisma models
    actual = load_schema_from_database()  # dari information_schema
    
    missing_in_db = expected.tables - actual.tables
    missing_in_code = actual.tables - expected.tables
    
    for table in expected.tables:
        missing_cols = expected.columns[table] - actual.columns[table]
        extra_cols = actual.columns[table] - expected.columns[table]
        
        if missing_cols:
            print(f"❌ {table}: kolom {missing_cols} ada di code tapi tidak di DB")
            print(f"   → Buat migration: npm run migrate:create add_{table}_cols")
            sys.exit(1)
        
        if extra_cols:
            print(f"⚠️  {table}: kolom {extra_cols} ada di DB tapi tidak di code")
            print(f"   → Update model atau buat migration untuk drop")
    
    if missing_in_db or missing_in_code:
        sys.exit(1)
    
    print("✅ Schema sinkron")
```

**Aturan emas untuk tim:**
1. **Setiap perubahan model = migration wajib** (no exception)
2. **Migration harus reversible** (selalu tulis `down` migration)
3. **CI menolak PR tanpa migration** jika ada perubahan model
4. **Staging DB harus di-reset mingguan** dari production schema (bukan dari migration history)

### 🎯 Task Baru: Akses Pribadi per Peserta Mediasi (Granular RBAC)

Ini adalah evolusi penting dari "workspace-level access" ke "participant-level access". Di mediasi konstruksi Indonesia, perbedaan ini krusial karena:

- **Pemohon (Claimant)** — Kontraktor yang mengajukan klaim
- **Termohon (Respondent)** — Owner yang diklaim
- **Mediator/Penilai Ahli** — Netral, tidak boleh melihat privileged documents
- **Pengamat (Observer)** — Bisa dari regulator, hanya lihat dokumen tertentu
- **Lawyer masing-masing pihak** — Punya akses privileged ke klien sendiri
- **Expert Witness** — Diundang khusus untuk isu teknis tertentu

**Model data yang direkomendasikan:**

```sql
CREATE TABLE mediation_participants (

    left_at TIMESTAMPTZ,
    removal_reason TEXT,
    
    -- Metadata
    display_name VARCHAR(100),
    contact_email VARCHAR(255),
    contact_phone VARCHAR(20),
    
    -- Verification

    kyc_verified_at TIMESTAMPTZ,
    kyc_verified_by UUID REFERENCES users(id),
    
    -- Constraints
    UNIQUE(matter_id, user_id),
    CONSTRAINT valid_role CHECK (role IN (
        'CLAIMANT', 'RESPONDENT', 'MEDIATOR', 'OBSERVER',
        'CLAIMANT_LAWYER', 'RESPONDENT_LAWYER', 'EXPERT_WITNESS'
    ))
);

-- Dokumen dengan klasifikasi granular
CREATE TABLE documents (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    matter_id UUID REFERENCES matters(id) NOT NULL,
    
    -- Klasifikasi
    classification VARCHAR(20) NOT NULL DEFAULT 'INTERNAL',
    -- 'PUBLIC', 'INTERNAL', 'RESTRICTED', 'MANAGERS', 'PRIVILEGED'
    
    -- Untuk RESTRICTED: daftar participant yang boleh akses
    -- (kosong = semua participant dalam matter)
    restricted_to_participants UUID[] DEFAULT '{}',
    
    -- Untuk PRIVILEGED: hubungan lawyer-client
    privileged_relationship JSONB,
    -- {"lawyer_user_id": "...", "client_user_id": "..."}
    
    -- Untuk INTERNAL: organisasi pemilik
    owner_organization_id UUID REFERENCES organizations(id),
    
    -- Metadata
    uploaded_by UUID REFERENCES users(id),
    uploaded_at TIMESTAMPTZ DEFAULT NOW(),
    title TEXT,
    description TEXT,
    file_checksum VARCHAR(64) NOT NULL,
    
    -- Legal hold
    legal_hold BOOLEAN DEFAULT false,
    retention_until DATE
);

-- View: dokumen yang bisa diakses user tertentu dalam matter tertentu
CREATE VIEW user_accessible_documents AS
SELECT 
    d.id AS document_id,
    d.matter_id,
    d.classification,
    d.title,
    mp.user_id,
    mp.role AS participant_role,
    CASE 
        WHEN d.classification = 'PUBLIC' THEN true
        WHEN d.classification = 'INTERNAL' 
            AND d.owner_organization_id = mp.organization_id THEN true
        WHEN d.classification = 'RESTRICTED' 
            AND mp.id = ANY(d.restricted_to_participants) THEN true
        WHEN d.classification = 'MANAGERS' 
            AND mp.role IN ('MEDIATOR') THEN true
        WHEN d.classification = 'PRIVILEGED' 
            AND mp.user_id IN (
                (d.privileged_relationship->>'lawyer_user_id')::uuid,
                (d.privileged_relationship->>'client_user_id')::uuid
            ) THEN true
        ELSE false
    END AS can_access
FROM documents d
JOIN mediation_participants mp ON mp.matter_id = d.matter_id
WHERE mp.status = 'ACTIVE';

-- Policy di level database (defense in depth)
CREATE POLICY document_access_policy ON documents
    FOR SELECT
    USING (
        EXISTS (
            SELECT 1 FROM user_accessible_documents uad
            WHERE uad.document_id = documents.id
              AND uad.user_id = current_setting('app.current_user_id')::uuid
              AND uad.can_access = true
        )
    );
```

**Service layer:**

```python
# services/access/participant_access_service.py

class ParticipantAccessService:
    """
    Menentukan apakah user tertentu bisa mengakses dokumen tertentu
    dalam konteks matter tertentu.
    """
    
    async def can_access_document(
        self, 
        user_id: str, 
        document_id: str,
        matter_id: str
    ) -> AccessDecision:
        
        # 1. Ambil data participant
        participant = await self.db.get_participant(matter_id, user_id)
        if not participant or participant.status != "ACTIVE":
            return AccessDecision(granted=False, reason="NOT_PARTICIPANT")
        
        # 2. Ambil data dokumen
        doc = await self.db.get_document(document_id)
        if doc.matter_id != matter_id:
            return AccessDecision(granted=False, reason="DOCUMENT_NOT_IN_MATTER")
        
        # 3. Evaluasi berdasarkan klasifikasi
        if doc.classification == "PUBLIC":
            return AccessDecision(granted=True, reason="PUBLIC_DOCUMENT")
        
        if doc.classification == "INTERNAL":
            if participant.organization_id == doc.owner_organization_id:
                return AccessDecision(granted=True, reason="SAME_ORGANIZATION")
            return AccessDecision(granted=False, reason="CROSS_ORGANIZATION")
        
        if doc.classification == "RESTRICTED":
            if participant.id in (doc.restricted_to_participants or []):
                return AccessDecision(granted=True, reason="EXPLICITLY_GRANTED")
            return AccessDecision(granted=False, reason="NOT_IN_RESTRICTED_LIST")
        
        if doc.classification == "MANAGERS":
            if participant.role == "MEDIATOR":
                return AccessDecision(granted=True, reason="MEDIATOR_ROLE")
            return AccessDecision(granted=False, reason="NOT_MANAGER_ROLE")
        
        if doc.classification == "PRIVILEGED":
            privileged = doc.privileged_relationship or {}
            if user_id in [
                privileged.get("lawyer_user_id"),
                privileged.get("client_user_id")
            ]:
                return AccessDecision(granted=True, reason="PRIVILEGED_RELATIONSHIP")
            return AccessDecision(granted=False, reason="NOT_IN_PRIVILEGED_REL")
        
        return AccessDecision(granted=False, reason="UNKNOWN_CLASSIFICATION")
    
    async def list_accessible_documents(
        self, 
        user_id: str, 
        matter_id: str
    ) -> list[Document]:
        """List semua dokumen yang bisa diakses user dalam matter"""
        return await self.db.query("""
            SELECT d.* FROM documents d
            JOIN mediation_participants mp ON mp.matter_id = d.matter_id
            WHERE mp.user_id = :user_id
              AND mp.matter_id = :matter_id
              AND mp.status = 'ACTIVE'
              AND (
                d.classification = 'PUBLIC'
                OR (d.classification = 'INTERNAL' 
                    AND d.owner_organization_id = mp.organization_id)
                OR (d.classification = 'RESTRICTED' 
                    AND mp.id = ANY(d.restricted_to_participants))
                OR (d.classification = 'MANAGERS' 
                    AND mp.role = 'MEDIATOR')
                OR (d.classification = 'PRIVILEGED' 
                    AND mp.user_id IN (
                        (d.privileged_relationship->>'lawyer_user_id')::uuid,
                        (d.privileged_relationship->>'client_user_id')::uuid
                    ))
              )
        """, {"user_id": user_id, "matter_id": matter_id})


class AccessDecision:
    granted: bool
    reason: str
    # reason digunakan untuk audit log dan error message ke user
```

## BAGIAN 4: TASK BERIKUTNYA YANG DIREKOMENDASIKAN

Berdasarkan pola "hardening" yang sedang Anda jalankan, berikut urutan logis task berikutnya:

### 🎯 Task #21: End-to-End Encryption untuk Dokumen PRIVILEGED (PRIORITAS TINGGI)

**Mengapa:** Access control di application layer tidak cukup. Jika database di-breach, dokumen privileged bisa terbaca. Perlu encryption di level storage.

**Approach:**
- Client-side encryption untuk dokumen PRIVILEGED
- Kunci enkripsi hanya dipegang oleh lawyer + client (bukan platform)
- Platform hanya menyimpan ciphertext
- Zero-knowledge architecture untuk privileged docs

### 🎯 Task #22: Rate Limiting & Anomaly Detection untuk API Dokumen (PRIORITAS TINGGI)

**Mengapa:** Mencegah data exfiltration oleh user yang kompromised.

**Approach:**
- Rate limit per user per matter (misal: max 100 dokumen/jam)
- Deteksi pola download massal (indikator exfiltration)
- Auto-suspend + alert ke security team
- Geofencing (block akses dari negara tidak biasa)

### 🎯 Task #23: Data Retention Policy Engine (PRIORITAS SEDANG)

**Mengapa:** UU PDP mewajibkan penghapusan data setelah tujuan tercapai. Matter yang ditutup harus punya lifecycle management.

**Approach:**
- Retention policy per klasifikasi dokumen
- Auto-archive setelah matter ditutup
- Auto-delete setelah retention period
- Legal hold override (untuk sengketa yang masih berjalan)

### 🎯 Task #24: Participant Self-Service Portal (PRIORITAS SEDANG)

**Mengapa:** Mengurangi beban mediator dalam mengelola participant.

**Approach:**
- Participant bisa update profil sendiri
- Request akses ke dokumen tertentu (dengan approval mediator)
- View audit trail akses mereka sendiri
- Withdraw dari matter (dengan konfirmasi)
